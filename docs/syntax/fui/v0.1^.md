# fncc `.fui` Language Syntax — V0.1^

> frozen for the V0.1^.x release series. The syntax introduced in v0.1 and preserved throughout the pre-1.0 series.

## 1. Purpose of this Specification

This document defines the syntax and semantics of the `.fui` template language used by the fncc compiler (`fncc-core`). It is the **authoritative reference** for parsing, code generation, and validation rules.

Implementations (parsers, code generators, LSP tooling) **must** conform to this specification to be considered compatible with fncc V0.1^.x.

## 2. Stability Policy

- The syntax described here is **frozen** for the entire V0.1^.x release series.
- No breaking changes to the syntax or semantics will be introduced within V0.1^.x.
- Future minor releases (v0.2, v0.3, …) **should** be backward-compatible with V0.1^ where possible. Breaking changes must be documented and gated behind a new spec version.
- Additions (new built-in elements, new directive syntax, etc.) **must not** silently change the meaning of valid V0.1^ files.

## 3. Grammar Overview

The `.fui` language is parsed with a [Pest](https://pest.rs/) PEG grammar defined in `crates/fncc-core/src/parser/fncc.pest`. The top-level structure is:

```
document = { SOI ~ frontmatter? ~ WS* ~ element ~ WS* ~ EOI }
```

A valid `.fui` file consists of:

1. **Optional frontmatter** delimited by `---` … `---`.
2. **Exactly one root element** (which may contain children).

### Pest Grammar (Normative)

```pest
document = { SOI ~ frontmatter? ~ WS* ~ element ~ WS* ~ EOI }

frontmatter = { "---" ~ (!("---") ~ ANY)* ~ "---" ~ WS? }

element = {
    open_tag ~ children? ~ close_tag
    | self_closing_tag
}

open_tag       = { "<" ~ tag_name ~ (WS ~ attr)* ~ WS? ~ ">" }
self_closing_tag = { "<" ~ tag_name ~ (WS ~ attr)* ~ WS? ~ "/>" }
close_tag      = { "</" ~ tag_name ~ WS? ~ ">" }

tag_name   = @{ (ASCII_ALPHA | "_") ~ (ASCII_ALPHANUMERIC | "_" | "-")* }
attr       = { attr_name ~ "=" ~ attr_value }
attr_name  = @{ (ASCII_ALPHA | "_") ~ (ASCII_ALPHANUMERIC | "_" | "-")* }
attr_value = { "\"" ~ (escape | (!"\"" ~ ANY))* ~ "\"" | interpolation }

children   = { node* }
node       = { inner_text | interpolation | element }

inner_text = @{ (!("{" | "<") ~ ANY)+ }

interpolation       = { "{" ~ interpolation_expr ~ "}" }
interpolation_expr  = { (ASCII_ALPHANUMERIC | "_" | "." | " " | "!" | "?" | "(" | ")" | "[" | "]" | "&" | "|" | "=" | "+" | "-" | "*" | "/")+ }

escape = { "\\" ~ ANY }
WS     = { " " | "\t" | "\n" | "\r" }
```

### Token Rules

| Token | Definition |
|---|---|
| `tag_name` | Starts with `[a-zA-Z_]`, continues with `[a-zA-Z0-9_-]*` |
| `attr_name` | Same character set as `tag_name` |
| `attr_value` | Either a double-quoted string (with `\"` escape support) or an interpolation expression |
| `inner_text` | Any characters that are not `{` or `<` |
| `interpolation_expr` | One or more characters from a restricted set: alphanumeric, `_`, `.`, space, `!`, `?`, `(`, `)`, `[`, `]`, `&`, `\|`, `=`, `+`, `-`, `*`, `/` |
| `WS` | Space, tab, newline, carriage return |

### Whitespace Handling

- Leading and trailing whitespace around the root element is ignored.
- Whitespace-only text nodes (`inner_text`) are discarded during parsing.
- Whitespace between attributes is required (one or more `WS` characters).
- Whitespace inside interpolation expressions is preserved verbatim (e.g., `{ state . count }` is valid).

## 4. File Structure

### 4.1 Frontmatter

Frontmatter is an optional block delimited by `---` on its own line (or at the start of the file). It may contain:

- **`@state` directive** — declares the component as stateful.
- **`use` declarations** — import paths for `.fui` components, props types, or Rust items.
- **Plain Rust code** — everything else passes through unchanged into the generated Rust output.

**Syntax:**
```fui
---
@state CounterState
use crate::prelude::*;
use gpui::TextInput;
use ui::components::Header;
use props::HeaderProps;
---
```

#### `@state` Directive

```fui
@state TypeName
```

- Declares that the component is stateful with state type `TypeName`.
- The generated code produces `impl Render for TypeName { … }`.
- A component with `@state` **must not** also use `<Slot>` or receive props.
- See [Section 8 — State](#8-state-state) for details.

#### `use` Declaration Variants

| Form | Meaning | Emitted in output? |
|---|---|---|
| `use ui::path::Name;` | Imports a `.fui` component at `src/ui/path/Name.fui` | No (stripped from frontmatter) |
| `use ui::path::{A, B};` | Grouped import of multiple `.fui` components | No |
| `use props::StructName;` | Declares the component receives a props struct | No |
| `use props::{X, Y};` | Grouped props imports | No |
| `use gpui::TypeName;` | Imports a GPUI Rust type | Yes (emitted as Rust `use`) |
| `use crate::…;` | Standard Rust import | Yes (emitted unchanged) |

### 4.2 Root Element

Every `.fui` file must have **exactly one root element**. The root element can be any valid element (built-in, imported component, or unknown).

### 4.3 Component Naming Convention

- The generated render function name is derived from the **file stem**, not the root element name.
- CamelCase file stems are converted to snake_case: `HeaderCard.fui` → `render_header_card()`.
- Example: `src/ui/components/Header.fui` → `pub fn render_header()`.

## 5. Elements and Attributes

### 5.1 Element Syntax

```fui
<tag_name attr1="value1" attr2="{expr}">
    children…
</tag_name>

<self_closing_tag attr1="value1" />
```

- Tag names must match the `tag_name` grammar rule.
- Elements must be properly balanced: `<A>…</A>` (matching tag names).
- Elements with no children may use self-closing syntax: `<Tag />`.

### 5.2 Attribute Syntax

```fui
<Text size="xl" data-id="{state.id}" />
```

- Attribute names must match the `attr_name` grammar rule.
- Values are either **double-quoted strings** or **interpolation expressions**.
- Boolean attributes (presence-only) are **not** supported in V0.1^. Every attribute must have a value.

### 5.3 Text Nodes

```fui
<Text>Hello, world!</Text>
```

- All non-whitespace text that is not inside `{…}` or `<…>` is treated as a text node.
- Text nodes are emitted as string literals in the generated Rust.
- Whitespace-only text nodes are discarded.

## 6. Interpolation Syntax (`{…}`)

### 6.1 Expression Interpolation

```fui
<Text>Count: {state.count}</Text>
<Text size="{state.level}">Details</Text>
```

### 6.2 Expression Resolution

| Interpolation | Stateful component | Stateless component |
|---|---|---|
| `{state.field}` | `self.field` | `self.field` |
| `{props.field}` | (not supported) | `props.field` |
| `{bare_expr}` | `self.bare_expr` | `self.bare_expr` |

- The `state.` prefix is **always** stripped and resolved to `self.` in the generated code.
- The `props.` prefix is kept verbatim (only valid in stateless components with props).
- Bare expressions (no prefix) are also prefixed with `self.`.

### 6.3 Interpolation in Attributes

```fui
<Text size="{state.size}">Content</Text>
```

The generated code calls `.to_string()` on the expression and uses it as the attribute value via `.child()`.

### 6.4 Valid Characters in Interpolation Expressions

The following characters are allowed inside `{…}`:

```
a-z A-Z 0-9 _ . ( ) [ ] ! ? & | = + - * / space
```

This supports basic Rust expressions like field access (`state.field`), method calls (`items.iter()`), and operators (`a + b`), but not all Rust syntax (e.g., no string literals, no `=>`, no `::` for paths).

## 7. Component Imports

### 7.1 Single Import

```fui
---
use ui::components::Header;
---
```

Resolves to `src/ui/components/Header.fui`. The component is usable as `<Header />` in the template.

### 7.2 Grouped Import

```fui
---
use ui::components::{Header, Footer, Card};
---
```

All three components must exist as separate `.fui` files under `src/ui/components/`.

### 7.3 Import Resolution Rules

- The `ui::` prefix maps to the `ui_dir` configured in `build.rs` (default: `src/ui`).
- Path segments map to directory components: `ui::components::Header` → `{ui_dir}/components/Header.fui`.
- Imported component files **must not** use `@state`. Only stateless components can be imported.
- The import path **must** match an existing `.fui` file; unknown imports produce a build error.
- Render function names derive from the file stem, not the tag name used in the template.

### 7.4 Component Usage

```fui
<Header />
<Header title="Welcome" subtitle="Hello" />
<Header>Child content for slot</Header>
```

- Self-closing syntax is valid for components with no slot.
- Components with `<Slot>` in their template accept children.
- Components with props (see [Section 11 — Props](#11-props)) accept named attributes that map to struct fields.

## 8. State (`@state`)

### 8.1 Declaration

```fui
---
@state CounterState
---
```

### 8.2 Semantics

- The generated code produces `impl Render for CounterState`.
- The render method has signature `fn render(&mut self, _window: &mut Window, cx: &mut Context<Self>) -> impl IntoElement`.
- State must be a Rust struct (typically `#[derive(Default)]`) defined in the application's Rust source.
- Access state fields in the template via `{state.field_name}` (resolves to `self.field_name`).

### 8.3 State Inference (Optional)

When semantic analysis is enabled (via `GenerateOptions.src_dir`), the compiler scans Rust source files for `#[fncc::command]` functions and infers the state type from their first parameter. If all commands in a `.fui` file reference the same state type, the `@state` directive may be omitted.

**Conflict detection:**

| Scenario | Result |
|---|---|
| `@state A`, commands use `&mut A` | ✅ Passes |
| `@state A`, commands use `&mut B` | ❌ Hard error |
| `@state A`, multiple command types | ❌ Hard error |
| No `@state`, commands use `&mut A` | State inferred as `A` |
| No `@state`, commands use different types | ❌ Hard error |

### 8.4 Stateful Component Restrictions

Stateful components **must not**:

- Use `<Slot>` (slots are only supported on stateless components).
- Receive props (`use props::…` with `{props.…}` interpolation).
- Use `onclick` with Level 1 or Level 2 commands (only Level 3 is supported in stateful components — the entity handle pattern is used for state mutation).

## 9. Commands (`onclick`)

### 9.1 Declaration

Commands are Rust functions annotated with `#[fncc::command]`:

```rust
#[fncc::command]
fn handle_click(state: &mut CounterState, cx: &mut Context<CounterState>) {
    state.count += 1;
    cx.notify();
}
```

### 9.2 Binding

```fui
<Button onclick="handle_click">+1</Button>
```

- The `onclick` attribute value is a bare string matching the Rust function name.
- The string **must not** be an interpolation expression; it must be a literal string.

### 9.3 Command Levels

| Level | Signature | Use case | Codegen pattern |
|---|---|---|---|
| 1 | `fn handler()` | Fire-and-forget | `.on_click(__fncc_cmd_handler)` |
| 2 | `fn handler(&ClickEvent)` | Access click data | `.on_click(__fncc_cmd_handler)` |
| 3 | `fn handler(&mut State, &mut Context<State>)` | Mutate state + re-render | Stateful: `handle.update(cx, \|this, cx\| { __fncc_cmd_handler(this, cx); })` |

### 9.4 Trampoline System

For each command function `fn foo(…)`, the `#[fncc::command]` macro generates a trampoline function:

```rust
#[allow(unused)]
fn __fncc_cmd_foo(…) { … }
```

- **Level 1 trampoline:** Accepts `(&ClickEvent, &mut Window, &mut App)`, ignores all args, calls `foo()`.
- **Level 2 trampoline:** Accepts `(&ClickEvent, &mut Window, &mut App)`, passes the event.
- **Level 3 trampoline:** Accepts `(&mut State, &mut Context<State>)`, passes both.

The codegen always references the trampoline (`__fncc_cmd_xxx`), so it does not need to know the user's signature at compilation time.

### 9.5 Validation

When semantic analysis is enabled (`src_dir` is provided):

- Every `onclick` value must match a `#[fncc::command]` function in the Rust source.
- Missing commands produce a hard build error.
- Duplicate command names (same function in multiple files) produce a hard build error.

## 10. Control Flow

### 10.1 `<If>` / `<ElseIf>` / `<Else>`

Conditional rendering via if/else-if/else chains.

```fui
<If condition="{state.show_details}">
    <Text>Details are visible</Text>
</If>
<Else>
    <Text>Details are hidden</Text>
</Else>
```

**Rules:**
- The `condition` attribute is required on `<If>` and `<ElseIf>`, and is an interpolation expression.
- `<ElseIf>` and `<Else>` **must** immediately follow an `<If>` or `<ElseIf>` without intervening elements or text.
- `<Else>` must be the last branch in the chain.
- An orphaned `<Else>` or `<ElseIf>` (without a preceding `<If>`) produces no output (the chain is discarded).
- An `<If>` following a previous `<If>` starts a **new** independent chain.
- A chain that ends without `<Else>` automatically gets an implicit `else { div() }` in the generated code.

**Generated Rust pattern:**
```rust
if self.show_details { div().child(div().child("Details are visible")) }
else { div().child(div().child("Details are hidden")) }
```

### 10.2 `<For>`

Iterative rendering over a collection.

```fui
<For each="{state.items}" let="item" index="i">
    <Text>{i}. {item.name}</Text>
</For>
```

**Attributes:**

| Attribute | Required | Description |
|---|---|---|
| `each` | Yes | Interpolation expression resolving to an iterable collection |
| `let` | No (default: `item`) | Variable name for each element |
| `index` | No | Variable name for the loop index (0-based) |

**Rules:**
- The `each` attribute must be an interpolation expression.
- The `let` value becomes the closure parameter name in `.map(\|item\| { … })`.
- When `index` is provided, the generated code uses `.enumerate().map(\|(i, item)\| { … })`.
- Inside the `<For>` body, `state.` expressions that match the loop variable are un-prefixed. For example, `{item.name}` within a `<For let="item">` generates `item.name` (not `self.item.name`). This uses identifier-aware replacement to avoid corrupting state fields that share a prefix.

**Generated Rust pattern:**
```rust
self.items.iter().enumerate().map(|(i, item)| {
    div().child(div().child(format!("{}", i)).child(div().child(item.name.to_string())))
})
```

## 11. Props

### 11.1 Defining Props

Props are defined in Rust using `#[derive(fncc::Props)]`:

```rust
#[derive(fncc::Props)]
pub struct HeaderProps {
    pub title: String,
    pub subtitle: Option<String>,
}
```

The `Props` derive macro (`fncc-macros`) is a marker; it generates no code. The build-script scanner (`fncc-core::semantic`) detects `#[derive(Props)]` structs and extracts field metadata for validation.

### 11.2 Receiving Props

In a `.fui` component, declare the props type import and use `{props.field}` interpolation:

```fui
---
use props::HeaderProps;
---
<Stack direction="vertical" gap="2">
    <Text size="xl">{props.title}</Text>
    <Text>{props.subtitle}</Text>
</Stack>
```

**Rules:**
- The component **must** have `use props::StructName;` in its frontmatter.
- `{props.field}` interpolation triggers the `props: &HeaderProps` parameter in the generated render function.
- If the template does not use `{props.…}`, no props parameter is added (even if `use props::…` is present).
- Only **stateless** components can receive props. Stateful components with `@state` cannot use props.

### 11.3 Passing Props

When using a component that expects props, pass attributes matching the props struct fields:

```fui
<Header title="Welcome" subtitle="Nice to see you" />
```

### 11.4 Caller-Side Validation

When semantic analysis is enabled, the following validation occurs at build time:

| Scenario | Error |
|---|---|
| Unknown attribute `<Header unknown="x" />` | `component 'Header' has no prop 'unknown' — available props: title, subtitle` |
| Missing required field `<Header />` (title: String) | `component 'Header' requires prop 'title' (type String)` |
| Optional field absent `<Header title="Hi" />` (subtitle: Option<String>) | ✅ Passes |
| All fields optional, none provided `<Msg />` | ✅ Passes |

### 11.5 Generated Code Pattern

**Component (receiver):**
```rust
pub fn render_header(props: &HeaderProps) -> impl IntoElement {
    div().flex().flex_col().gap(px(2.))
        .child(div().text_3xl().child(props.title.to_string()))
        .child(div().text_base().child(props.subtitle.to_string()))
}
```

**Caller:**
```rust
render_header(&HeaderProps {
    title: "Welcome".into(),
    subtitle: "Nice to see you".into(),
})
```

## 12. Composition

### 12.1 `<Fragment>`

Groups multiple children without introducing an additional DOM element. Useful for returning multiple children from a conditional or list.

```fui
<Fragment>
    <Text>First</Text>
    <Text>Second</Text>
</Fragment>
```

**Codegen:** The generated code flattens `<Fragment>` children into the parent's `.child()` chain — no wrapper `div()` is added beyond the normal layout.

**Rules:**
- Attributes on `<Fragment>` are ignored.
- `<Fragment>` can be nested inside `<Stack>`, `<If>`, `<For>`, and other elements.

### 12.2 `<Slot>`

A placeholder for child content passed by the parent. Enables component composition similar to React `children`.

**Defining a component with a slot:**
```fui
---
use props::CardProps;
---
<Stack direction="vertical" gap="4">
    <Text size="xl">{props.title}</Text>
    <Slot />
</Stack>
```

**Using a component with a slot:**
```fui
<Card title="Hello">
    <Text>Child content goes here</Text>
</Card>
```

**Rules:**
- `<Slot>` is only supported in **stateless** components (no `@state`).
- Stateful components **must not** use `<Slot>`.
- A component with `<Slot>` generates a render function with `children: impl IntoElement` parameter.
- When calling a component with a slot, children are passed as the `children` argument.
- Self-closing usage `<Card title="Hello" />` passes `div()` as the children (no-op).

**Generated signature:**
```rust
pub fn render_card(props: &CardProps, children: impl IntoElement) -> impl IntoElement { … }
```

**Generated call:**
```rust
render_card(&CardProps { title: "Hello".into(), }, div().child(div().child("Child content goes here")))
```

## 13. Built-in Elements

### 13.1 `<Stack>`

A flex container. Maps to GPUI's `div().flex()`.

| Attribute | Values | Behavior |
|---|---|---|
| `direction` | `"vertical"` or `"horizontal"` (default: horizontal) | Adds `.flex_col()` when vertical |
| `gap` | Number string (e.g., `"12"`, `"12.5"`) | Adds `.gap(px(n.))` |

**Examples:**
```fui
<Stack direction="vertical" gap="16">…</Stack>
<Stack direction="horizontal" gap="8">…</Stack>
```

### 13.2 `<Text>`

A text label. Maps to GPUI's `div()` with text-sizing utility calls.

| Attribute | Values | Behavior |
|---|---|---|
| `size` | `"xs"`, `"sm"`, `"base"`, `"lg"`, `"xl"`, `"2xl"` / `"xxl"`, `"3xl"` | Adds `.text_xs()`, `.text_sm()`, `.text_base()`, `.text_lg()`, `.text_xl()`, `.text_2xl()`, `.text_3xl()` |
| (unknown value) | anything else | Falls back to `.text_base()` |

**Examples:**
```fui
<Text size="xl">Large heading</Text>
<Text>Default size</Text>
<Text>Count: {state.count}</Text>
```

### 13.3 `<Button>`

A clickable button. Maps to GPUI's `div()` with `cursor_pointer()` and `on_click()`.

| Attribute | Values | Behavior |
|---|---|---|
| `onclick` | String matching a `#[fncc::command]` fn name | Binds click handler |

**Examples:**
```fui
<Button onclick="handle_click">+1</Button>
<Button onclick="log">Log</Button>
```

**Codegen behavior:**
- The button's `id()` is derived from its text content (e.g., `+1`).
- In stateful components, click handlers use the entity handle pattern to mutate state:
  ```
  .on_click({
      let handle = handle.clone();
      move |_, _, cx| { handle.update(cx, |this, cx| { __fncc_cmd_xxx(this, cx); }).ok(); }
  })
  ```
- In stateless components, the trampoline is passed directly:
  ```
  .on_click(__fncc_cmd_xxx)
  ```

### 13.4 Unknown / Fallback Elements

Any element that is not a built-in, not an imported `.fui` component, and not a gpui import with a registered render function falls through to the fallback codegen:

```fui
<CustomEl foo="bar">content</CustomEl>
```

Generates:
```rust
div().attr("foo", "bar").child("content")
```

All attributes are passed through as `.attr(key, value)` calls. Children are appended normally.

This pattern supports:
- Arbitrary GPUI div-level customizations.
- Elements imported via `use gpui::…` that the codegen doesn't know about.
- Future component types before dedicated codegen is added.

### 13.5 Reserved Built-in Element Names

The following element names are **reserved** and cannot be used as imported component tag names in the template (built-in handling takes precedence over imports):

| Element | Type | Precedence |
|---|---|---|
| `Stack` | Built-in layout | Matches before import lookup |
| `Text` | Built-in text | Matches before import lookup |
| `Button` | Built-in button | Matches before import lookup |
| `If` | Control flow | Matches before import lookup |
| `ElseIf` | Control flow | Matches before import lookup |
| `Else` | Control flow | Matches before import lookup |
| `For` | Control flow | Matches before import lookup |
| `Fragment` | Composition | Matches before import lookup |
| `Slot` | Composition placeholder | Matches before import lookup |

Even if a component is imported as `<Text>`, it will use the built-in codegen, not the import. Use different tag names for imported components that provide text-like functionality.

## 14. Validation Rules (Summary)

### 14.1 Parse Errors (Hard, from Pest)

| Condition | Result |
|---|---|
| Empty file / whitespace only | Parse error |
| Unclosed tag: `<Text>foo` | Parse error |
| Unopened close tag: `</Text>` | Parse error |
| Mismatched close tag: `<Div></Text>` | Panic (assertion) |
| Invalid tag name: `<123foo>` | Parse error |
| Unclosed frontmatter: `---\n@state Foo\n<Root>` | Parse error |
| Invalid attribute: `<Text size=>` | Parse error |
| Unquoted attribute value: `<Text size=xl>` | Parse error |

### 14.2 Import Validation (Hard, from Build Script)

| Condition | Error |
|---|---|
| Imported `.fui` file not found | `import {path} -> file not found at {path}.fui` |

### 14.3 Semantic Validation (Hard, when `src_dir` is provided)

| Condition | Error |
|---|---|
| `onclick` command not found in Rust source | `command {name} not found` |
| `@state` type conflicts with inferred type | `@state {A} conflicts with inferred state type {B}` |
| Commands reference multiple state types | `commands reference multiple state types` |
| Duplicate `#[fncc::command]` definitions | `duplicate #[fncc::command] fn {name}()` |
| Unknown prop attribute | `component {name} has no prop {attr}` |
| Missing required prop field | `component {name} requires prop {field} (type {type})` |

### 14.4 Structural Rules (Hard, from Build Script)

| Condition | Error |
|---|---|
| Stateful component uses `<Slot>` | `stateful components cannot use <Slot>` |
| Stateful component uses props | `component cannot have both state and props` |
| Imported component uses `@state` | (Not explicitly forbidden, but imported components with state are not supported — the import resolution does not pass state to the caller) |

## 15. Complete Examples

### 15.1 Minimal Stateless Component

**`src/ui/Greeting.fui`:**
```fui
<Text size="xl">Hello, fncc!</Text>
```

**Generated:**
```rust
pub fn render_greeting() -> impl IntoElement {
    div().text_xl().child("Hello, fncc!")
}
```

### 15.2 Stateful Counter

**`src/ui/App.fui`:**
```fui
---
@state CounterState
---
<Stack direction="vertical" gap="12">
    <Text size="xl">Count: {state.count}</Text>
    <Button onclick="handle_click">+1</Button>
</Stack>
```

**`src/main.rs` (Rust):**
```rust
use fncc::*;

include!(concat!(env!("OUT_DIR"), "/generated.rs"));

#[derive(Default)]
struct CounterState {
    count: i32,
}

#[fncc::command]
fn handle_click(state: &mut CounterState, cx: &mut Context<CounterState>) {
    state.count += 1;
    cx.notify();
}

fn main() {
    Application::new().run(|cx: &mut App| {
        cx.open_window(WindowOptions::default(), |_, cx| {
            cx.new(|_| CounterState::default())
        }).unwrap();
    });
}
```

### 15.4 Control Flow and Composition

**`src/ui/App.fui`:**
